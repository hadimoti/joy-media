The eight lanes are `hosted-verify`, `node-contracts`, `linux-real-services`, `windows-candidate`, `real-service-acceptance`, `fixture-acceptance`, `acceptance-responsive` and `p3-real-services`. `release-candidate-v2.yml` is unchanged, and its SHA-256 is pinned in `release-candidate-v3.test.ts`.

**Critical path, as implemented.** The acceptance chain is `real-service-acceptance` → `fixture-acceptance` → `p3-real-services` → `gate-summary`. It no longer waits for `windows-candidate`, so the gate starts when the slower of two lanes finishes: the Windows lane, or the chain. The chain is about 40 + 15 + 7 + 3 ≈ 65 minutes on the plan's estimates and v2's measurements. The Windows lane is not measured for v3; v2 took 70.7 minutes for its equivalent work. So the implemented path is about max(Windows, chain), not Windows plus the chain.

### 2.2 Review of the implemented graph (Codex gpt-6.1-sol, read-only, 2026-10-26)

Each finding was checked against the code before any change. The fixes are in the branch, and each has a policy test or a negative control.

1. **Blocker, fixed.** The collection ran without the PostgreSQL environment the shards had. Suites registered with `describe.skipIf(!JOY_TEST_DATABASE_URL)` (for example `apps/api/src/usdc-invoice-ledger.pg.test.ts`) ran in the shards but were not listed, so the merge would fail. The collection now runs in `hosted-prepare` with the shards' database environment.
2. **High, fixed.** A listed test that a run skipped counted as executed. The merge now requires every listed test to run to a verdict, and a listed skip fails it. Unlisted platform skips are still recorded, and they do not count.
3. **High, fixed in v3, owner decision for v2.** `vitest.p0.config.ts` spreads the default suite's `projects`, so its own include list is ignored. Measured, it collects 6,839 default-suite entries and none of the P0 files. The v3 lanes use `vitest.p0-v3.config.ts`, which collects the 10 P0 files (176 entries). `vitest.p0.config.ts` and `release-candidate-v2.yml` are unchanged, because v2 uses them. See the owner decisions.
4. **High, fixed.** Real-service did not start first. The harness required the Windows file before its pass completed (`real-service-acceptance.mjs`). A v3-only mode, `JOY_MEDIA_CI_WINDOWS_EVIDENCE=deferred`, skips that check. The final gate still requires and binds the Windows receipt (`restore-retained-evidence.mjs`), so an absent, foreign or malformed receipt still fails the release. The default stays strict for v2.
5. **Medium, fixed.** Fixture acceptance and P3 were skipped after an upstream failure. They now run after validation, as the design section 2 says, so one run reports every failure.
6. **Medium, fixed.** The shadow summary step did not fail when a builder failed (`set -uo pipefail` without `-e`).
7. **Medium, fixed.** The v3 coverage receipts (hosted report, readiness record and run summary) were not kept with the final evidence. They are now copied beside it with checksums, and the verify step checks them.
8. **Low, fixed.** The P3 janitor had no token, so it could not classify other runs.
9. **Medium, fixed.** The Windows teardown suppressed process-inspection errors and could pass with an unknown process state. It now fails closed.

Not changed, deliberately:

- **Caching** of the pnpm store and Playwright browsers. The review estimates 0 to 3 minutes, and a shared cache needs a trust review first. Measure before adding it.
- **More hosted shards.** The count stays at three. Under the review's own proxy (eight times the local shard times, one worker per job), the hosted branch is shorter than the acceptance chain, so more shards would not shorten the critical path. Measure the hosted shard times before changing the count.
- **A compact Windows verification receipt** that would replace the gate's byte-level checks. It changes the gate's inputs, and the verification needs to be designed first.
- **Duplicate Windows work**: the lifecycle reruns three CLI source files. `windows-lifecycle.ps1` is shared with v2, so changing it is an owner decision.

## 3. Budget check (plan target: ≤ 75 min)

The plan's estimate counts only the acceptance-runner chain: real-service about 40, fixture about 15, P3, and gate about 3 minutes, with one P3 pass at or under about 15 minutes. Measured inputs:

| Input                       | Plan estimate                    | Measured in v2                         | Used here               |
| --------------------------- | -------------------------------- | -------------------------------------- | ----------------------- |
| Real-service pass           | about 40 (39–41)                 | 44.4 and 44.6                          | 44.5                    |
| Fixture acceptance (merged) | about 15                         | not measured                           | 15                      |
| P3 pass                     | at most about 15 (the condition) | 7.1 and 7.0                            | 7.0                     |
| Gate                        | about 3                          | 9.0, including the download v3 removes | 3, and 9 for comparison |

Acceptance chain: 44.5 + 15 + 7.0 ≈ 67 min, then the gate.

v3's gate also needs the Windows lane's digests (job outputs), so the end-to-end time is the longer of the two lanes, plus the gate:

- The merged Windows lane (`windows-candidate`) is not measured. In v2 the same work took 70.7 min.
- If the merged lane takes 70.7 min, the total is about 73.7 min with a 3-minute gate, or about 79.7 min with the measured 9-minute gate.

The plan's estimate does not include the Windows lane, so the 75-minute target is not yet supported by measurement. Measure the merged lane in a shadow dispatch (D18) before stating the target as a result. Below 60 minutes would need a second acceptance runner, which is an owner dependency outside this scope (plan §3.4).

## 4. Flakes and retries

- No retries: `--retries=0` and `--retry=0`, and a guard fails any run whose `GITHUB_RUN_ATTEMPT` is not 1. The only retries left are hash-verified downloads. Under v3, any flake costs a new SHA.
- The "survives" flake is identified: `apps/desktop/src/jobs/local-worker.integration.test.ts`, test "local Worker route (real worker process, real FFmpeg) > survives a Worker killed mid-job: the lease expires instead of hanging, and a restarted Worker completes new work". It failed in the static job of ci-dev run 40118338118 (see the [2026-10-25 P0 file](../qa/evidence/2026-10-25-v103-p0-ci-timing.md)). v3 has no retry to absorb it, so it needs a root-cause fix before the P4 freeze. Reproduction under load is not done yet.
- The `onTaskUpdate` RPC timeout under host load: reproduce under synthetic CPU load, cap Vitest pool concurrency, move process-spawning e2e tests into a serial project, and require 30 or more loaded runs with zero timeouts from the scheduled job (plan L10).
