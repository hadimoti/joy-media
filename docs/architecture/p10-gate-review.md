## Known gap: no bridge from `VisualObjectV1` to pixels exists anywhere in the codebase

Investigated directly for this gate review. Confirmed by exhaustive search:

- No function anywhere (`visualObjectToRenderNode` or equivalent) converts a `VisualObjectV1` (`image`/`text`/`shape`/`camera`/`null`) into a `RenderNode`/`RenderFrameIR` (`@joy-media/render-ir`).
- The P04 gate reel (`tooling/golden-render/src/first-party-scenes.test.ts`) that proved "footage + captions + two HTML scenes export through H.264/AAC" does so with a **hand-authored** `RenderFrameIR` fixture (`createParitySpikeFrame`) and HTML-scene-surface captures — never a `VisualObjectV1`.
- `evaluateAnimatedTransform`, `evaluateCameraTransform`, `evaluateExpressionTransform`, and `evaluateCameraExpressionTransform` (the entire P04/P10 motion+camera+expression evaluator surface) all return a plain `VisualObjectTransformV1`. None of them, and nothing downstream of them, ever constructs a `RenderNode`.
- `apps/editor-web`'s Inspector/Motion/Camera panels edit `VisualObjectV1` state; nothing in `apps/editor-web` reads `@joy-media/render-ir` for that state. The editor has had no live pixel-preview canvas since P01 (`monitor` is a label-only placeholder) — flagged separately during WP-10.2 and already accepted by the owner as a background task.

**This predates P10 — it is a P01–P04-era architectural gap, not a P10 regression.** P10's camera and expression features are the first work to make this gap consequential for a literal "renders through the real export path" claim, because P04's motion system (parenting, keyframes) was never bridged to pixels either; P10 inherits and surfaces that pre-existing limitation rather than introducing it.

**Consequence for this gate:** the first exit criterion is marked **Partial**. Every non-rendering part of the claim (correct camera+expression composition, parallax math, no-regression guarantee) is proven with real production code and tests. The literal "through the real render/export path" phrase cannot be honestly claimed until a `VisualObjectV1 → RenderNode` bridge exists — which is a substantial, separate piece of work (design a mapping for four object kinds, asset/font resolution, group composition for parenting, and wiring into `renderer-pixi`/`renderer-headless`), not something that belongs inside a gate-review WP. It is the same underlying gap as the already-flagged "no live preview canvas" background task (`task_6f29897c`, in progress as of this review) — building the canvas requires building this exact bridge, so that task's scope will need to grow to cover it.

## Scope boundary

P10 is bounded by ADR-0015 to exactly two capabilities: a depth-only 2.5D camera (no yaw/pitch, no per-layer 3D tilt) and a restricted expression language. The other eight P10 parking-lot items (multicam, color/HDR, paint/vector tools, audio restoration, interchange formats, render-farm, publishing integrations, enterprise governance) and a true 3D camera remain closed — opening any of them requires its own ADR. The `VisualObjectV1 → RenderNode` rendering bridge, while now a known and documented gap, is explicitly **not** part of P10's scope; it is a cross-cutting, pre-existing limitation for a future part to close.
