# P10 — Advanced Professional Systems (Optional / LATER)

**Status:** in-progress · **Gate to enter:** P09-era, owner approval per capability (ADR-0015) · **Master plan:** §36 Phase 10, §20.3
**Goal:** Open exactly the P10 capabilities the owner selects, one ADR at a time; everything else in the parking lot stays closed.

**Scope opened 2026-07-20 (ADR-0015):** a bounded 2.5D depth camera and a restricted/sandboxed expression language. Both extend P04's motion system (§20.3 "later motion system").

## Work packages

- [x] **WP-10.1 — Camera core** _(done 2026-07-20)_. `positionZ` depth joins `VisualObjectTransformV1` and the animatable-property set (keyframeable via the existing curve engine, no expression engine needed); `kind: 'camera'` objects carry a vertical field of view; compositions may declare an `activeCameraId`. New `camera-core` package composes parent-chain depth and a pure depth-only perspective projection (dolly/track/roll/zoom; **no yaw/pitch, no per-layer 3D tilt** — ADR-0015) that reduces to the existing `VisualObjectTransformV1` shape, so Render IR and every renderer adapter are untouched. The evaluator exposes `evaluateCameraTransform`; the undoable `composition.setActiveCamera` command rides the shared v1 history. No active camera ⇒ byte-for-byte identical output to pre-P10 projects.
- [x] **WP-10.2 — Camera UI** _(done 2026-07-20)_. Undoable `camera.create`/`camera.remove` (removal rejected while still an active camera or a parent — a foreign-key guard, not cascade logic) and `camera.setFieldOfView` commands round out the camera command surface. A new Camera panel creates/selects camera objects (its own local selection, since cameras carry no timeline clip), edits position/depth/roll/FOV/parent, and picks the active camera per composition. Verified live: create → activate → dolly the depth field → undo three times (value, active-camera, creation itself all cleanly reverse) → redo three times (all restore) → reload (state persists through the durable command log). **Known gap, not this WP's to close:** editor-web has no live pixel-preview canvas at all yet (`monitor` is a label-only placeholder across every P00–P09 session) — parallax correctness is proven by camera-core/evaluator's tests calling the real projection function, not by an on-screen rendered comparison.
- [x] **WP-10.3 — Restricted expression engine** _(done 2026-07-20)_. New `expression-core` package: a hand-written tokenizer/recursive-descent parser/tree-walking interpreter for arithmetic, comparisons, logical/ternary, and an allowlisted numeric function set (`sin`/`clamp`/`lerp`/…) plus a deterministic hash-seeded `random(seed)` — no `eval`/`Function`/`with` anywhere, and the grammar has no loop or user-defined-function production, so evaluation cost is bounded by (limit-checked) AST size, not by runtime detection. `compileExpression` never throws — malformed/oversized/disallowed input comes back as coded diagnostics (`EXPRESSION_PARSE_ERROR`, `EXPRESSION_TOO_LARGE`, `EXPRESSION_UNKNOWN_FUNCTION`, `EXPRESSION_REF_ARGS`). Cross-object dependencies are explicit `ref("objectId", "property")` calls whose arguments **must** be string literals, so every dependency is statically known before evaluation; `detectExpressionCycle` finds cycles across a reference graph without ever running anything. A parser depth limit (64) defends against real JS stack-overflow from adversarial nesting like `((((...))))`, separate from the interpreter's own instruction-count guard (10,000 steps) which holds even against a hand-built AST that skips the parser. 50 tests, including a dedicated forbidden-capability suite: static source-scan proving no `eval`/`Function`/`with` string appears anywhere in the package, and runtime proof that `document`/`window`/`process`/`globalThis`/`Date`/`fetch`/etc. are unreachable (identifiers resolve only through an explicitly injected context — nothing falls through to any ambient global). No `project-schema` dependency — this is the engine only; wiring it onto `VisualObjectV1` is WP-10.4.
- [x] **WP-10.4 — Expression schema + evaluator + UI** _(done 2026-07-20)_. `VisualObjectV1` gains an optional `expressions` map (source text per animatable channel); project-schema validates shape only (non-empty string, known channel) since it cannot depend on `expression-core` (§9.1). `motion-core`'s new `resolveObjectTransformWithExpressions` overrides a channel's curve/static value with its expression's result — memoized by source text — and falls back gracefully with a diagnostic on any compile/eval failure, including a recursion guard for `ref()` chains that degrades safely (and whose diagnostics correctly propagate up through nested references, not just the top-level channel) if a cyclic project is ever reached at evaluation time. The undoable `object.setExpression` command (in `motion-core`, delegated by `property-system` like the other object commands) rejects a malformed expression or one that would create a reference cycle (via `buildExpressionReferenceGraph` + `detectExpressionCycle`, checked before commit) by throwing — matching `validateAnimationCurve`'s existing precedent — with a pre-state inverse for undo/redo. The evaluator exposes `evaluateExpressionTransform` (camera-core's projection intentionally does not yet consume it — documented follow-on). The Inspector gained a per-channel "ƒx" toggle revealing an inline expression editor; a channel with an expression disables its keyframe/numeric controls and shows the evaluated result, with any diagnostic shown inline. **Two real bugs caught only by live browser verification, both fixed in this WP:** (1) the Inspector's displayed value used curve-sampling even when a channel had an expression, so an expression's result was silently masked by a pre-existing keyframe curve — fixed by giving expressions display precedence, matching the resolver's actual precedence; (2) `object.setExpression` validates by throwing, but the Inspector's commit handler didn't catch it, so typing a malformed expression threw uncaught instead of showing the inline error — fixed by wrapping the dispatch in try/catch and keeping the editor open with the message on failure. Verified live: `sin(time) * 50` on Position X correctly overrode a pre-existing 0→300 keyframe curve and matched the expected value at multiple playhead positions; an invalid expression showed its exact parse-error message inline without crashing; fixing and re-committing it succeeded; undo correctly reverted the expression (channel returns to its plain static/curve value) and redo restored it; the committed expression survived two full page reloads through the durable command log.
- [ ] **WP-10.5 — Gate review.** Combined evidence: a reel using a moving 2.5D camera across depth-offset layers plus at least one restricted expression, rendered through the real export path; forbidden-expression-capability tests (no DOM/network/wall-clock reachable); cycle detection rejects a self-referential expression; a composition with no active camera renders identically to its pre-P10 output (regression guard).

## Exit criteria (bounded scope only — ADR-0015)

- [ ] A composition with a keyframed/dollying 2.5D camera renders correct parallax across depth-offset layers through the real render/export path.
- [x] A composition with no `activeCameraId` is byte-for-byte unaffected (no regression to any P00–P09 render or golden) — proven by `evaluateCameraTransform`/`resolveObjectTransformThroughCamera` test parity with the pre-P10 parenting-only resolver.
- [x] Restricted expressions cannot reach DOM/network/filesystem/process/wall-clock; a runaway or cyclic expression fails as a diagnostic, never a crash or hang — proven at the engine level (`expression-core`'s forbidden-capability suite + `compileExpression`/`detectExpressionCycle`); WP-10.4 surfaces this per-property in the Inspector.
- [x] Expression and camera edits are undoable/redoable and survive reopen through the durable command log — verified live for both (WP-10.2, WP-10.4) and by test.
